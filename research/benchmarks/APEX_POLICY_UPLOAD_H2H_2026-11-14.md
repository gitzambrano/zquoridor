## Binary integrity and provenance

The uploaded ZIP contains a 4.01 Windows UCI engine, an architecture
manifest, a baseline INT8 network, an Apex policy INT8 network, and a
README containing historical test claims.

| Network | SHA-256 | Bytes |
| --- | --- | ---: |
| Uploaded Apex policy | `fe8473255fd219fab247b1a7d44be25384a6cfc5daa5c301def49109badb7f2b` | 1,093,668 |
| Uploaded original 4.01 | `45fa3ea7db3127a0b907a23d268b0c55c2020e1018513d54bb920cdbe134abe0` | 1,093,668 |
| Current production 4.10 policy | `fe8473255fd219fab247b1a7d44be25384a6cfc5daa5c301def49109badb7f2b` | 1,093,668 |

The uploaded Apex network is **byte-for-byte the current 4.10 production
network**, as established by the complete SHA-256 match with
`data/nnue/release.json` and `docs/releases/4.10.md`.

Binary comparison of the two uploaded networks finds a completely identical
prefix of 985,824 bytes. All 101,805 differing byte positions are in the
remaining 107,844-byte policy tail. These byte offsets match the 4.10
release's documented policy-only update. The value features and value
heads are unchanged; no new value architecture is present.

The archive README reports 136.5/212 points (64.4%) against original 4.01
using a 4.01 search binary, but no individual game records are included in
the uploaded ZIP. This self-reported number is not an independent new
result for the current 4.10 search. The repository's earlier production
release reports 54.125% over 400 games with an earlier search configuration;
its improvement confidence interval includes parity.

## Controlled new tournament

[GitHub Actions 64-game job](https://github.com/gitzambrano/zquoridor/actions/runs/43637497864)

Protocol:
- One **identical native 4.10 executable** for both sides; only the
  `--nnue` network path changes.
- Apex/production INT8 hash exactly
  `fe8473255fd219fab247b1a7d44be25384a6cfc5daa5c301def49109badb7f2b`.
- Historical INT8 network extracted from repository commit
  `6e8efb08f7a9442f795f4c3110db3135d70eadf9`, required to match
  `45fa3ea7db3127a0b907a23d268b0c55c2020e1018513d54bb920cdbe134abe0`.
- Fixed **200 ms per move**, standard referee, no pondering; each selected
  opening played with both colors, bootstrap summary at paired opening level.
- 16 paired openings in Normal and 16 paired openings in Center Rush,
  randomized with fixed seed 20261114, split into two disjoint shards per
  opening book. Total 32 paired openings / 64 games. No source training data
  is generated by this tournament.
- Each shard uploads `games.jsonl` and `summary.json`; the combined
  result must aggregate the four shards, not average independent Elo values.
- Screening-sized result: even 64 games cannot replace the full promotion
  gate, and this is not a candidate-vs-production comparison because the
  uploaded Apex network **is production**.

## Decision

There is no novel policy to merge or promote from the archive. If the
controlled match establishes any advantage, it confirms the choice already
made in release 4.10, rather than revealing a new upgrade. Maintain
the current search and network, regardless of the 4.01 Windows binary.

## Completed 64-game policy-only H2H results

All four shards completed successfully with the exact expected weights
SHA-256 checks and the same 4.10 search executable. Zero failed games,
no missing pairs, no pondering, no invalid moves. Search was 200 ms
per move, with color-reversed paired openings.

| Book | Paired openings | Games | Apex/4.10 score |
| --- | ---: | ---: | ---: |
| Normal | 16 | 32 | 59.375% |
| Center Rush | 16 | 32 | 59.375% |
| **Total** | **32** | **64** | **59.375% (38/64 points)** |

The point estimate is **+65.92 Elo** (score-to-Elo conversion).
A 20,000-resample bootstrap over **the 32 paired opening scores**
gives an approximate 95% score interval of **48.44% to 70.31%**.
This interval includes parity. Individual 8-pair shard Elo values
must not be averaged. Every game ended at a legal goal.

The outcome is compatible with the archived 4.10 policy being somewhat
better than the original 4.01 head under the current search, but it
does **not** establish a reliable positive Elo gap on its own.
Most importantly, it demonstrates no new upgrade: the uploaded
Apex weights are byte-for-byte identical to production 4.10.
